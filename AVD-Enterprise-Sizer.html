📐 Microsoft VM Sizing Best Practice Multi-session VMs: 4–24 vCPUs recommended. Under 4 = unstable UI. Over 32 = diminishing returns from synchronization overhead. For 20+ users, use multiple smaller VMs with breadth-first load balancing. Source: MS Learn — Session host VM sizing guidelines
📐 Application Group Types — Desktop vs RemoteApp
  • Full Desktop (Desktop Application Group): Users receive a complete Windows desktop experience with Start menu, taskbar, and all installed apps. One Desktop app group per host pool. Available on both pooled and personal host pools.
  • RemoteApp (Remote Application Group): Individual applications are published and streamed to the user's local device — they appear as native windows alongside local apps. Multiple RemoteApp groups per host pool. Available on pooled host pools only (not personal).
  • Desktop + RemoteApp on same host pool: A pooled host pool can have both — one Desktop group and multiple RemoteApp groups. However, if a user is assigned to both types on the same pool, they only see the preferred application group type (configured at the host pool level) — not both. Assign different users to each type.
  • Personal host pools: Only support Full Desktop. RemoteApp is not available for personal pools.
  • Developer Scenarios: Developers typically benefit from Full Desktop with Personal host pools (1 VM per dev) for Visual Studio, Docker, Git, and debugging. RemoteApp on pooled pools works for publishing specific dev tools (e.g. SSMS, VS Code) to teams that don't need a full desktop.
Source: MS Learn — AVD Application Groups · Preferred App Group Type

📐 BCDR Decision Guide (Microsoft Learn)
  • HA Approach:
    • Single Region — Uses Availability Zones within one region. VMs spread across 3 fault-isolated zones. Lowest cost, protects against datacenter-level failures but not region-wide outages.
    • Active-Passive — Primary region serves all users; a standby environment in a secondary region activates during failover. ~30% additional cost for standby resources. Best for most enterprise scenarios.
    • Active-Active — Both regions serve users simultaneously. Near-zero downtime but ~80% additional compute cost. Use only for mission-critical workloads requiring <1 hour RTO.
  • RTO (Recovery Time Objective):
    • 4 hours — Mission-critical. Requires pre-provisioned standby VMs and automated failover scripts.
    • 8 hours — Standard enterprise. Allows time to deploy session hosts from golden image in DR region.
    • 24 hours — Non-critical workloads. Manual intervention acceptable; rebuild from scratch in DR region.
  • RPO (Recovery Point Objective):
    • 1 hour — Near-continuous replication. Requires FSLogix Cloud Cache or premium storage with frequent snapshots.
    • 4 hours — Standard. GRS storage replicates asynchronously (~15 min lag) with 4-hour backup intervals.
    • 24 hours — Daily backups. Acceptable for stateless pooled desktops where profiles rebuild quickly.
  • Profile Replication:
    • FSLogix Cloud Cache — Active-active profile sync to multiple storage targets. Users can failover seamlessly. Higher IOPS consumption and VM memory usage.
    • GRS Storage — Azure-managed async geo-replication (~15 min RPO). Lower cost but requires manual failover and profiles may be slightly behind.
  • Backup Strategy:
    • Azure Backup — Native integration. Protects FSLogix file shares (daily snapshots, 30-day retention) and personal VM disks. Supports cross-region restore.
    • None (stateless pooled) — Valid when all pooled desktops are stateless and profiles are stored externally on replicated storage. No VM-level backup needed.
Source: MS Learn — AVD Disaster Recovery | Business Continuity Plan
